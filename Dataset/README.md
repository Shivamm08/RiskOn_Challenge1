# Knowledge Base — Synthetic Suitability Wiki

This is a **stand-in** for the real Julius Baer Suitability Wiki extract,
which is only released at the event. It exists so retrieval, reasoning, and
the eval harness can be built and tested *today* against realistic,
regulatorily-accurate content — then pointed at the real HTML dump on Day 1
with no code changes (same file structure: raw HTML pages + a page index).

## What's here

| File | What it is |
|---|---|
| `generate_wiki.py` | Generates `wiki/*.html` — 23 pages covering every topic referenced in JB's real evaluation set |
| `wiki/` | The generated HTML pages (raw HTML, matching the real delivery format) |
| `page_index.json` | Filename → title → topic tags → region scope, generated by the script above |
| `build_eval_set.py` | Generates `evaluation_set.json` |
| `evaluation_set.json` | 28 questions digitized from JB's real evaluation set PDF, each with expected behavior (answer / clarify / answer-with-scope-limit) and expected source page(s) |
| `eval_harness.py` | Scores the pipeline against `evaluation_set.json` — **this is what proves the confidence score is calibrated, not just plausible-looking** |

## Why this content is trustworthy, not just plausible

Every page was written to directly satisfy JB's own real evaluation
questions and to reproduce — and correctly resolve — every failure mode JB
documented in their existing assistant (JAI):

- **Icon/table interpretation** — `alerts_config_advisory_location.html` has an explicit active/inactive table with an icon legend, and the DTM/Trade Basic distinction is stated unambiguously.
- **Scope limits** — `client_classification_global.html` is explicitly scoped to CH only and says so; Monaco has its own page with its own `MC_Local` class.
- **Acronym resolution** — `own_one_way_notification.html` states plainly that OWN = One Way Notification, not "Own Investment Strategy."
- **Hard-block instructions** — `cpr_handling.html` states plainly that the RM must NOT proceed while a CPR alert is visible, and that client risk-acceptance does not override it.
- **Graphics that must be read** — `product_risk_methodology.html` and `pe_order_placement.html` contain inline SVG diagrams, matching JB's note that some answers require reading a graphic, not just text.
- **Genuinely ambiguous questions** — 5 of the 28 evaluation questions are marked `expected_behavior: "clarify"` because the real question (e.g. "how long do I have to fix a concentration risk alert") depends on unstated context (Advisory Session vs Client Book) — the correct system behavior is to ask, not guess.

## How this connects to the rest of the system

- **Topic tags are shared vocabulary** with `data/generate_smes.py` — every wiki topic has at least one SME who can be routed to, cross-validated (see build log).
- **`eval_harness.py`** is not just a nice-to-have — running it and showing the resulting accuracy/confusion breakdown in the pitch is the actual evidence that the confidence score means something, which is what a RegTech-founder and a former bank CRO on the judging panel will want to see instead of a bare number on the UI.

## Swapping in the real Wiki dump on Day 1

1. Replace the contents of `wiki/` with the real HTML files.
2. Regenerate `page_index.json` to reflect the real page titles/structure (the real dump won't have topic_tags or region_scope metadata — these need to be inferred by the ingestion pipeline, which is exactly the kind of reasoning the challenge is scoring).
3. Re-run `eval_harness.py` against JB's real evaluation set (replacing `evaluation_set.json`) to get real accuracy numbers for the pitch.
